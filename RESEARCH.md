## Reminders example (2026-09-14)

The fifth example reworks the SQLiteData `Examples/Reminders` app into the architecture of the other four: core package `reminders` (`Reminders`, `Reminders SQLiteData`, `Reminders Feature`), Apple package `reminders-apple` (`Reminders View`, `Reminders App`), one host `Reminders`, five test targets. `Tools/generate_project.py` now lives in the repository and regenerates hosts, projects, host schemes, the workspace, and the aggregate scheme (57 buildables, 26 testables). Rulings and reasons:

- **Domain first.** The reference computes everything in SQL (`@FetchAll` with `where`/`order`, FTS5 for search, triggers for positions and the default list). Here `Lists` is one value and every rule is a function on it: stats, detail membership and ordering, search, the completion grace period, manual reordering, tag renaming across reminders, deleting a list with its reminders. The stored form only loads and persists the whole graph (`Lists.load`, `Lists.persist` upserts every row and deletes the absent ones) and the feature persists on every change. This is the point of the example: the same rules serve a server or a web layer without a database.
- **Everything durable is in SQLite.** The reference keeps per-detail ordering and show-completed in `AppStorage` under one key for every tag detail, and the open detail in view state. Here they are `Lists.Detail.Preference` rows keyed by `Lists.Detail.ID` (one key per tag set, order-independent) and a `listsState` row, so relaunch restores the detail the user was in with its ordering.
- **Typed identifiers.** `Reminder.ID`, `Reminder.List.ID`, `Tag.ID` (`Tagged<Tag, String>`, the title), and `Lists.Detail.ID` are `Tagged`, stored as columns through the `Tagged` trait of `sqlite-data`; search tokens are `Lists.Search.Token.near(String)` or `.tag(Tag.ID)`. The direct `swift-structured-queries` dependency the first pass declared for the trait was unnecessary and is gone; `sqlite-data`'s own trait forwards it (Xcode's build log shows `-DTagged` on `StructuredQueriesCore`).
- **Grace period.** A tapped reminder becomes `.completing`; it counts as completed everywhere (counts, the Completed detail) but stays on screen and in place in its detail so the tap can be undone, and completed reminders sort last only when the detail shows them, as in the reference; `onChange(of: store.lists.completing, initial: true)` runs the five-second timer, restarted by every tap (TCA26 cancels the tasks an `onChange` added before it runs again) and revived at mount if the app quit mid-period. The cross-check against the reference found the first pass hid completing rows immediately; fixed.
- **Dropped on purpose:** CloudKit sync and sharing, list cover images and their assets table, the FTS5 trigram index (search matches title, notes, and tags case-insensitively in memory; `NEAR` tokens are plain text matches and there is no highlighting), TipKit, the 200-character note truncation. Search results order by open-first then due date like a detail; the reference ordered by SQLite's `NULL`-first due date.
- **Xcode built and ran it; `xcodebuild -derivedDataPath` did not:** the latter did not apply the trait (`Reminder.ID is not representable as a column`). The headless Xcode MCP session on the workspace builds and tests everything.

Two defects the tests and the device run found the same evening, both in the way TCA26 is used, and both fixed across all five features where they applied:

- **A store task's state change is invisible to `TestStoreActor` until `expect`.** `TestStoreActor.expect` consumes modifications that store tasks already queued and returns their tasks; it never waits. The mount loaded the stored value in a task, so the first `expect { _ in }` in every feature test raced the database read; Reminders lost the race (a larger graph) and the load overwrote the toggled reminder after the test's action. Ruling: `onMount { state in … }` loads synchronously through GRDB's synchronous `read` (a small local database, and SQLiteData's own `@FetchAll` fetches synchronously at first), seeding stays a task, and tests no longer need the leading `expect`. The completion timer's change still needs one `expect` after the tap.
- **`Binding(_:)` on an optional traps when the sheet dismisses.** The form sheets used `if let draft = Binding($store.reminder)`, SwiftUI's force-unwrapping projection; when Save or Cancel set the draft to `nil` the dismissing sheet re-read the binding and crashed (`EXC_BREAKPOINT` in `BindingOperations.ForceUnwrapping.get`, `Reminders-2026-09-14-190249.ips`). This was the crash seen whenever a form closed in the device hub. Ruling (principal, 2026-09-14 evening): the forms are TCA26 child features, `Reminder.Feature` and `Reminder.List.Feature` (each owning its draft), presented as `Lists.Feature.Destination` through `ifLet(\.destination) { Destination.body }`; the sheets bind to `$store.scope(\.destination).reminder` and `.list`, so SwiftUI holds a scoped store that outlives the dismissal and nothing force-unwraps. Save and Cancel stay parent decisions (`.destination(.reminder(.saveButtonTapped))` upserts the draft and clears the destination); tag intents route through the child to the parent's lists. A `Binding.unwrapped(or:)` helper was tried first and rejected in favour of the destination shape.

**Pushed screens read the store themselves (2026-09-14 ~20:15).** The principal found that Sort By in a list detail worked once and then stopped. A device audit reproduced it and narrowed it: the preference changed and persisted (a swipe-flag on any row re-rendered the screen in the new order; a relaunch showed it), so only the view was stale. Cause: `Root` built `Lists.Detail.View(detail, lists: store.lists, …)` inside the `navigationDestination(item:)` closure, and SwiftUI does not re-run that closure for later store changes, so the pushed value view kept the lists captured at its first refresh. TCA26's case studies never do this: a pushed screen takes the store and reads it in its own body (`Presentations.swift`, `FeatureBindings.swift`), as the reference's `RemindersDetailView` observes its model. Ruling: `Root.Detail` in `Reminders App` is the pushed screen; it holds the store, reads `store.lists` in its body, and constructs the value view from it. `Reminders View` stays store-free. The same audit noted that row changes were not animated (the reference gets them from `@FetchAll(animation: .default)`); `.animation(.default, value: lists)` on the detail list and on the home list supplies them. Two minor findings fixed with it: a tag added from the form in a different case created a twin in the draft (the parent now owns the tag intents and writes the accepted tag back into the draft; `Lists.tag(titled:)` finds it case-insensitively), and show-completed in search reset only when the text emptied, not when the last token was removed (`onChange(of: store.search.isActive)`).

Device re-check of that build (20:18–20:21): Priority, Title, Due Date, Manual selected in a row re-ordered the rows every time with the subtitle tracking; Hide/Show Completed flipped on four consecutive toggles; the completion fill cross-fades and the row stays in place.

Point-Free's own skills for these libraries (`pfw-sqlite-data`, `pfw-structured-queries`, `pfw-tca26`) were consulted after the first pass. Applied: `bootstrapDatabase` keeps its documented name and stays the app's single entry; database errors go through `withErrorReporting` (`IssueReporting` declared explicitly in each `<Example> Feature` target) rather than `try?`; `@Dependency` stays, as TCA26's examples use it under the `Dependencies` trait; `onMount`/`onChange` mutate the `inout` state and only add tasks. Not adopted: `@FetchAll` in views (the domain-first rule keeps queries out of views) and FTS.

## Reminders static review, wave 2 (2026-09-15, morning)

The decoupling wave, under the ruling that the Point-Free Way takes priority, then TCA26's examples, then the sqlite-data Reminders example. Neither example offers a precedent for value-in/callbacks-out views (TCA26's views take stores, the reference row talks to the database), so the grouped shape is this repository's own. Applied: the inline editor's Date and Time chips are feature intents (`datePresetSelected`, `timePresetSelected`, run by `Lists.set(datePreset:for:at:calendar:)` and its time twin on the feature's clock and calendar), so the view no longer calls a mutating domain method and the rules are exercised by a feature test; the two form features carry `isNew`, decided by the parent at presentation, instead of `Root` looking the draft up in the lists; `Reminder.Row.Actions` (complete, delete, details, optional edit) and `Reminder.Editor.Actions` (complete, details, submit, setDate, setTime) collapse the row callbacks of `Lists.Detail.View` and `Lists.Search.View`, built once each in `Root` and `Root.Detail`; `Lists.stored` is the value without the editing place, and the feature persists on changes to it; the domain rules that touch a calendar take `calendar: Calendar = .current`, the feature passes `@Dependency(\.calendar)`, `Reminder.Form` has no wall-clock default, and the feature's default state is empty rather than the clock-reading sample. Test targets fleet-wide link only the tested target plus `ComposableArchitectureTestSupport` and `DependenciesTestSupport` where imported (the sibling tests already imported them transitively); the Reminders feature tests are exhaustive `TestStoreActor` tests, asserting each change through the domain method that made it, with child snapshots built by `snap(_:)`. The TCA26 checkout has no `\.exhaustivity` dependency, only the `TestExhaustivity` task-local, so the trait the skill names does not exist here; the four sibling feature tests still use the task-local. `bootstrapDatabase` traces every statement in Debug (log while live, console in previews, nothing in tests), as the skill has it.

Persistence was rewritten on the measurement rather than the assumption. `Lists.persist` now reads the stored value inside its own transaction and writes only rows that differ, deleting only rows that are gone; comparing against a baseline carried in memory was rejected because a persist cancelled and rolled back by the next change would leave its rows unwritten, while a read in the same transaction cannot. `remindersTags` keys on the pair, no surrogate. The first measurement, on the iPhone 17e with the trace streamed from the simulator, still showed every dated reminder upserted on each keystroke: the seed's `now` carries microseconds, the rows keep milliseconds, so the loaded value never equalled the value in memory. `Reminder.Record.isStored(as:)` compares dates within a millisecond, and the storage test seeds with a sub-millisecond clock. Re-measured: one keystroke in an inline row is six SELECTs and one upsert of the edited reminder in one transaction (nine traced lines with BEGIN and COMMIT); Done is the six reads and the state row; before this wave the same keystroke rewrote every list, tag, reminder, tagging (delete-all then re-insert), preference, and the state row, about fifty writes. Tests 72/72 on the aggregate scheme. The relaunch during the measurement reopened the Personal list, navigation being data.

## SQLite as the source of truth (2026-09-15, afternoon)

The whole-graph model was replaced. `Lists` no longer holds lists, reminders, tags, preferences, and the open detail as one value that the feature mutated and `Lists.persist` reconciled back into SQLite by comparing the graph and deleting what was absent; that mechanism, `Lists.load`, the in-memory CRUD and cascade rules, and the Swift filtering, sorting, and counting are gone. The records live in the tables; `Reminders SQLiteData` exposes one targeted operation per user intent (`Reminder.Record.toggle`, `insert`, `insert(after:)`, `update(from:to:)` writing only the columns and tags that differ, `delete`, `reorder`, `completeCompleting`, `deleteCompleted(matching:dueBefore:)`; `Tag.Record.add`, `rename` merging onto an existing title in any case, `delete`; `Reminder.List.Record.insert`, `update`, `delete(_:replacement:)` keeping a default list, `reorder`; the preference and state-row setters) and three `FetchKeyRequest`s (`Lists.Home.Request`, `Lists.Detail.Request`, `Lists.Search.Request`) that read a whole screen in one transaction and re-read when any table they touch changes. `Lists.Feature.State` holds them as `@Fetch` properties (`home`, `contents`, `results`), excluded from debug snapshots so exhaustive tests assert the feature's own state and read the observed values explicitly; the detail and search requests are reloaded from `onChange` on the detail, the editing place, and the search input. Membership, ordering, and counts moved into SQL; Swift's `localizedCaseInsensitiveContains`, a case-insensitive prefix rule, and `localizedCaseInsensitiveCompare` are installed as database functions and a collation so text matching and title order keep the app's semantics rather than `LIKE`'s ASCII folding. The row being edited keeps its place through a `CASE` on its identifier in the `ORDER BY`, which is what `editingPlace` did in memory. Inline editing is a draft (`Reminder.Editing`: draft, original, place) committed when editing ends by any route; the commit writes only what changed against the original, so an external change to another field survives, and it never inserts, so a row deleted meanwhile stays deleted. The grace timer is a task mounted on a counter bumped by every circle tap (`onMount(id:)`), which gives the latest tap the full period and cancels a stale timer; it checks the table before sleeping, so a relaunch mid-period resumes it, and its final `UPDATE` touches only rows still completing. TCA26 cancels the tasks of a repeated action, so every write inside a task is the synchronous `database.write`: the write lands before cancellation is observed, and only the state update after it can be skipped. Failures: the mount distinguishes an uninitialised database (the state row is absent: seed the sample) from one that cannot be read (`failure`, nothing seeded); a sheet's failed save keeps the draft and shows the reason, Done retries, and a record deleted under an open sheet is reported rather than recreated. Verified: 45/45 tests through the Xcode MCP on the iPhone 17e, and a device pass of restore, inline editing, chips, the grace period, and the sheet. The pre-existing failure of `tags order case-insensitively wherever they are listed` (Swift's `<` puts "Car" before "adulting") is resolved by the collation, in the test's favour; `Lists.Ordering` now lists Manual first, as the view test and the stock menu have it.


## Inline persistence, sessions, and the grace timer (2026-09-15, evening)

The review of the afternoon's refactor found the inline draft reaching SQLite only when editing ended, task results applied to whichever session was on screen, the grace timer started by a counter independent of the status write, "today" decided by SQLite's `localtime`, and tag identity folded by `NOCASE`. The corrections: `Reminder.Editing` is now draft, `saved` (what the database holds as far as the session has written it), place, and a session `UUID`; `onChange` of the draft writes the difference from `saved` at once, so typing survives termination, and a failed write keeps the draft, sets the session's `failure` (and the app's), and leaves `saved` where it was, so the next change or Done writes the whole difference again; ending or switching editors never drops a draft that could not be written, and a row deleted by another writer ends the session on the next keystroke without recreating it. Forms and editing sessions carry a session identifier and every task result is applied only if that session is still presented (`endEditing(session)`, `modifyReminderForm(session)`), forms carry `isSaving` so Done is one save. The audit of TCA26: a task that never suspends cannot observe the cancellation a repeated action causes and runs to its end, state change included, which is why the session check exists rather than relying on cancellation; the writes stay synchronous, so they land whole and in order. The grace timer is driven by a `@Fetch` of `Reminder.Record.Completing` in the state: TCA26 evaluates the body under observation tracking, so the observed query changing remounts the feature and `onChange(of: store.completing)` restarts (or, on an empty set, cancels) the timer for taps, reversals, deletions, and other writers alike; the mount loads the query before applying the restored state, so the loaded reader is the one observed. Days are `Range<Date>` bounds from the injected calendar (`Lists.day(containing:calendar:)`), passed to the requests; the feature moves the day at midnight on the injected clock and on `appActivated`, which the app sends when the scene becomes active. The tags table's key is declared on the `localizedCaseInsensitive` collation, with a migration that rebuilds the table and the links, keeping the older of two titles that were twins under NOCASE. Tests use no Combine: a test waits on an observed query through `Observations` on a `@Fetch` of the same request (one shared reader per request and database), under a real-time deadline, and controls time with `TestClock` per test.

## Scale investigation (2026-09-16)

Scope: what the screens feel at Extreme (`Reminder.Sample.Scale.extreme`, 100 lists × 1,000 reminders, 200 tags; ~40% of reminders carry 1–3 tags, 20% completed, 8% flagged, a third dated). Seeding itself is out of scope except where it bears on the screens. Measured with a throwaway test in the SQLiteData test target (deleted again): a `DatabasePool` on disk in WAL mode, as the app opens it, seeded with `generated(.extreme, seed: 1)`, every statement profiled through `db.trace(options: .profile)`, plans through `EXPLAIN QUERY PLAN`, and GRDB `ValueObservation`s started on the four requests to see which ones a write re-runs. Numbers are the iPhone 17e simulator on this Mac, Debug; the device is slower by a constant factor, the shapes are the same.

### What is slow or breaks

**1. The `tagList` subquery scans the tags table once per row.** Every row the screens read (`Reminder.Record.rows()`, `Reminder.Record+Statements.swift:104-116`) carries `$0.tagList` (`Reminder.Record+Queries.swift:75-80`), a correlated subquery joining `remindersTags` to `tags` on `remindersTags.tagID = tags.title`. The tags key is declared `COLLATE "localizedCaseInsensitive"` (`Schema.swift:84`) while `remindersTags.tagID` is plain text; SQLite takes the collation of the left operand, BINARY, so the tags index cannot serve the lookup and the planner chooses `SCAN tags` (200 rows) then probes the links index once per tag:

```
CORRELATED SCALAR SUBQUERY 1
  SCAN tags
  SEARCH remindersTags USING COVERING INDEX sqlite_autoindex_remindersTags_1 (reminderID=? AND tagID=?)
```

That is 200 index probes per reminder row, for every query that reads rows. Measured, same query, three forms of the subquery:

| rows read | as shipped | join reversed (`tags.title = remindersTags.tagID`) | no join (`group_concat(tagID)`) |
|---|---|---|---|
| one list, 803 rows | 33 ms | 5 ms | 3.5 ms |
| All, 79,977 rows | 3.28 s | 0.48 s | 0.33 s |

Reversing the join makes the comparison use the tags key's collation, so the plan becomes `SEARCH remindersTags (reminderID=?)` then `SEARCH tags USING COVERING INDEX (title=?)`: one probe per link. This one line is the largest single cost in the app; it is in the detail (every filter), search results, and every `find(id).rows()` read-back the feature does.

**2. Smart lists at 100k read and materialise tens of thousands of rows.** `Reminder.Filter.Detail.Request` (`Reminder.Filter.Detail.Request.swift:31-36`) fetches every matching row and maps each to a `Reminder` (parsing the tag list into a `Set`), then the view puts them all in one `SwiftUI.List` (`Reminder.Filter.Detail.View.swift:114`). Measured request time, shipped code:

| filter | rows | fetch |
|---|---|---|
| a list | 803 | 45 ms |
| Today | 224 | 21 ms (full scan of 100k, `coalesce()` around the range defeats any index) |
| Flagged | 8,055 | 0.42 s |
| Completed | 20,023 | 1.0–1.4 s |
| Scheduled | 26,814 | 1.4 s |
| All | 79,977 | 4.2 s |

Roughly 0.85 of the time is item 1; the remainder is the scan, the `ORDER BY` temp b-tree and the row materialisation. Opening All at Extreme is a four-second blank screen followed by an 80,000-row List. Nothing here is broken at Large (All = ~12k rows, ~0.6 s) but it is the ceiling.

**3. Observations re-fetch synchronously inside the write, on the main thread.** sqlite-data's `@Fetch` builds `ValueObservation.tracking` (`sqlite-data/Sources/SQLiteData/Internal/FetchKey.swift:121`), which GRDB treats as a non-constant region: after a commit that touches the region, the fresh value is fetched **on the writer connection, inside `databaseDidCommit`** (`GRDB/ValueObservation/Observers/ValueConcurrentObserver.swift:739-775`), and delivered by sqlite-data's `ImmediateScheduler` on that same thread. The feature's `write` is the synchronous `database.write` on the store's isolation (`Reminder.Feature.swift:490`). So every write the feature makes blocks the main thread for the write **plus every observed query whose region it touched.** GRDB's regions are column-level, so the fan-out is narrower than feared — measured per write, with the observed regions:

- `overview`: `lists(*), reminders(due,flagged,id,listID,status), remindersTags(tagID), tags(title)` — not re-run by title or notes typing.
- `detail`: whole `reminders` table (all columns) + `remindersTags`, `tags`, `lists`, `preferences` — re-run by any reminder change anywhere, in any list (the primary key is TEXT, so GRDB cannot narrow the region to rows).
- `pending`: `reminders(id,status)`.
- `results`: empty while idle (`Reminder.Search.Results.Request.swift:21` returns early, so an idle search costs nothing); the same as `detail` while active.

| write | re-fetched | main-thread time, shipped |
|---|---|---|
| one title keystroke, 1,000-row list open | detail | 60 ms |
| the same with search "the" active (57k matches) | detail + results | 3.5 s |
| completion toggle | detail, overview, pending, results | 3.6 s with search active; ~0.1 s without |
| new row (insert + placeLast) | all four | as above |

At 60 ms per keystroke the inline editor in a 1,000-row list drops frames on every character; after item 1 the detail read is ~6 ms and typing is fine. The search case is the one that breaks: with a broad search active, every completion tap on a result stalls the UI for seconds.

**4. Search runs two full scans per keystroke, twice.** `Reminder.Search.Results.Request` does `completedCount` (one scan calling the Swift `localizedCaseInsensitiveContains` function on 100k titles and notes, 91 ms) and the rows query (a second scan plus item 1 per match: 576 ms for "the report", 4,018 matches; 3.7 s for "the", 57,752 matches). Every change of the text (`Reminder.Feature.swift:457-462`) calls `results.load`, which fetches once through `asyncRead` and then subscribes a new observation that fetches again — two reads per character, off the main thread but queued behind each other, so results arrive late and out of step with the field. Suggestions (`#w`) are instant: 200 tags.

**5. The view layer at these row counts.** `Reminder.Filter.Detail.View.swift:137` and `:145` each build `detail.rows.map(\.id)` on every body evaluation — the body re-evaluates on every keystroke of the inline editor — which is two 80,000-element arrays per character in All. `Tag.Cloud.Flow` (`Tag.Row.swift:58-91`) measures all 201 pills in `sizeThatFits` and again in `placeSubviews` with no layout cache, on every home layout pass (the home body re-evaluates on every overview change). `Reminder.Row` formats its due date with `Date.FormatStyle` per row per render (`Reminder.Due+Description.swift`), which is what stock does too; no formatter is created per row. The Details sheet's list picker and the suggestion strip are 100- and 200-item views and are fine.

**6. Indexes.** `reminders` has one index, `listID` (`Schema.swift:142`); `remindersTags` has its primary key plus `reminderID` and `tagID` indexes. `pending` is a full scan on `status` (5 ms, re-run on every status change); Today filters `due` through `coalesce(due >= ? AND due < ?, 0)` (`Reminder.Record+Queries.swift:31`), which no index can serve. Neither is large, both are cheap to fix. Ordering columns (`position`, `created`, `title COLLATE`) always sort within a list of ≤1,000 rows through a temp b-tree — not worth indexes.

**7. Memory (for the record).** The 100k `Reminder` values are 18 MB, not the problem; the process footprint grows ~75 MB per `DatabasePool` after the 39 MB write and `pool.releaseMemory()` brings it back (103 → 29 MB). The app's Debug trace expands ~21 MB of SQL text during a seed and costs nothing measurable in time. Seeding time itself (4.9 s here) is flat for chunks ≥100 rows (50: 1.55 s per 20k; 100–2,000: 0.69–0.74 s), so the shipped 200 is right. None of this affects the screens; left alone.

### Plan, ranked by what the user feels

1. **Reverse the `tagList` join** (`Reminder.Record+Queries.swift:78`: `$1.title.eq($0.tagID.text)`). 7–10× on every row read: list detail 45 → ~6 ms, All 4.2 → ~0.6 s, search rows 3.7 → ~0.5 s, and the per-keystroke synchronous re-fetch (item 3) falls with it. Test: the plan of `Reminder.Record.rows` no longer contains `SCAN tags`.
2. **Debounce the search read** (`Reminder.Feature.swift:457`): wait ~250 ms on the feature's clock after a text change before `results.load`; token changes, showCompleted, and an emptied text load at once. Removes the pile-up of two full scans per character. Test: text changes do not read until the clock advances; a submit reads at once.
3. **Index `due` and `status`, and drop the `coalesce`** so Today uses the index: migration adding `idx_reminders_due` (partial, `WHERE due IS NOT NULL`) and `idx_reminders_status`; `isDue` becomes `due IS NOT NULL AND due >= ? AND due < ?`. Today 21 ms → <1 ms, pending 5 ms → <1 ms on every status change. Test: the migrated schema has the indexes and the Today plan uses one; the day boundary tests still pass.
4. **Window the smart lists.** All/Scheduled/Completed at 100k should not fetch 80k rows into one List. Give `Reminder.Filter.Detail.Request` a `limit` (e.g. 500) and return `total`, with a "Show more" row that raises the window; the detail's `rows` stays what it is. This is a design change (the domain type gains `total`), so it is proposed here and not done in this pass.
5. **Take the observed re-fetches off the main thread.** Two options: (a) `try await database.write` for the writes that do not need ordering with the next action (autosave, toggles), accepting GRDB's writer queue as the serializer; or (b) keep the synchronous writes and make the reads cheap (items 1 and 3 do most of this). Recommend (b) now and (a) only if a device trace still shows hitches after 1–3. The autosave could also debounce like the search (~300 ms), at the cost of losing the last 300 ms of typing on a relaunch mid-edit; the commit paths already write the whole difference, so nothing else changes. Not done in this pass.
6. **Compute `detail.rows.map(\.id)` once per body** in `Reminder.Filter.Detail.View` (a `let ids` used by both `.animation` and `.onChange`), and give `Tag.Cloud.Flow` a layout cache of measured sizes so 200 pills are measured once per invalidation, not twice per pass. Small; view-only.
7. **Fold `completedCount` into the rows scan** (one pass instead of two) and consider a results cap with a count for very broad searches. Follow-on to 2.

Items 1–3 are implemented below, each with a test; 4–7 are proposed.
